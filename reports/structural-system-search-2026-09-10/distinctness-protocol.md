# Distinctness and evidence protocol for a structural trading-system search

**The next feasible action is an audited system registry and a representative implementation tranche, not a claim that 10,000 genuinely different profitable systems already exist.** This protocol defines how to count them honestly. It does not establish that a universe of 10,000 independently defensible systems can be assembled, that any generated mathematics is original, or that the current data can test them all. This is advisory research; no runtime changes or new trades are authorized or performed by this artifact.

## Resolve what “new” means

These are separate claims, each requiring different evidence:

| Claim | Required evidence | What does not establish it |
|---|---|---|
| New implementation | Versioned code and comparison to existing implementations | Renaming a file or parameter |
| New to this engine | Repository inventory showing the mathematical decision structure was absent, plus its provenance | A familiar method applied to ETH instead of BTC |
| New structural system using established mathematics | An explicit decision/estimation/control architecture, nearest-family comparison, and a material structural distinction | A Cartesian product of indicators, lookbacks, stops and weights |
| Original mathematics or original-to-literature system | A derivation, stated novelty claim, literature comparison and independent scrutiny | An unfamiliar equation generated by an agent or lack of one search result |
| Empirically profitable system | Market-appropriate, after-cost evidence at the specified risk and capital scale, followed by frozen prospective evaluation | Distinct mathematics, syntactically unique equations or a profitable reused-data backtest |

A broad search can begin with an inventory of established methods while the intended novelty standard is clarified. Do not quietly substitute that inventory for a request for 10,000 original inventions.

## System identity and count rules

Define a structural system as the causal map from information available at time t and current account/order state to a distribution, target position or executable control action, together with the economic mechanism it intends to exploit. Its identity card must contain:

1. Economic mechanism and a falsifiable reason returns could exceed all costs; its null hypothesis and foreseeable failure regime.
2. Information set with publication/availability timestamps, estimation state, initialization and update equations.
3. Model or estimating assumptions, objective/loss, decision/control equations, action space and stopping/exit logic.
4. Execution contract and complete funded or margined cash-flow accounting.
5. Nearest existing systems, normalized equations, lineage and an explanation of the material distinction.
6. A synthetic admissible-history witness illustrating the structural difference, plus ablations explaining its cause.
7. Primary provenance and novelty label; implementation/data status; test, source and result hashes.
8. Separate system ID, variant ID, search-trial ID and statistical-comparison cohort.

The comparison must abstract away nuisance choices before assessing structure: asset name, units, ordinary thresholds, lookbacks, seed, code language, equivalent state encodings and algebraic rearrangements. Normalize operator graphs and equations; inspect exact simplifications and known reparameterizations; run common synthetic histories that expose drift, reversals, gaps, flat prices, regime switches, spread changes and inventory pressure. Compare temporal dependence and state transitions, not just output formulas.

A witness showing different behavior at one arbitrary parameter choice is insufficient: different lookbacks would pass that weak test. Reviewers must also explain why an admissible nuisance reparameterization does not remove the material distinction. A finite set of probes cannot certify global functional equivalence or non-equivalence. Ambiguous cases remain “distinctness unresolved” and are excluded from a certified structural count.

Conservative counting examples:

| Change | Count treatment |
|---|---|
| SMA 40 days to SMA 50 days | Same mathematical template; another configuration and search trial |
| BTC signal to ETH signal | Same template; another market application and trial |
| Price-minus-average versus price/average with equivalent transformed threshold | Algebraic/reparameterization equivalence where conditions match; no new structure |
| Replace one feature with another in the same threshold rule | Feature variant; a new economic mechanism requires its own supported causal thesis |
| Swap an MA estimator for a genuinely different latent-state likelihood/filter | Potential new estimator/system structure; compare assumptions, state evolution and decision effects |
| Average, vote or choose among existing signals with fixed weights | Composite configuration; retain lineage, do not multiply primitive-method count |
| New joint inventory/control problem with material feedback coupling | Potential new integrated system if its equations and counterexamples demonstrate the coupling |
| Add a different stop, fee assumption, leverage or instrument | Risk/execution/contract variant unless a different control problem is derived and independently justified |
| Enumerate every operator/feature/weight combination | Generated candidate expressions, not automatically distinct mathematical systems |

Keep separate counters for economic mechanisms, mathematical templates, integrated systems, implementations, parameter configurations, attempted evaluations and observed distinct signal paths. These are not interchangeable. Structural distinctness also does not imply statistically independent returns.

## What the previous “100” actually contained

Inspection of `tools/profit-search.py`, `screen/protocol.json`, and the completed independent `screen-audit.json` under `reports/profit-search-100-2026-09-10/` establishes:

- **100 registered configurations:** ten labeled asset/family groups times ten lookbacks.
- **Six decision templates:** SMA hysteresis, endpoint momentum hysteresis, close-channel breakout, trend-conditioned z-score pullback, relative-momentum rotation, and multi-window SMA consensus.
- **Four recurring scalar statistic types:** moving average, endpoint return, rolling extrema and standardized deviation. Rotation and consensus compose existing statistics and add selection/aggregation structure.
- **Ten labeled groups:** the six templates become ten groups by splitting the first four between BTC and ETH.
- **94 unique observed target paths:** a dataset-specific behavioral count; neither mathematical independence nor originality.
- **Seven zero-activity configurations**, including `pullback_btc-090` and `pullback_eth-090`, whose entry conditions are contradictory because the trend and pullback averages coincide.
- **Zero demonstrated original-to-literature mathematical inventions.** Six templates is a source-code taxonomy, not a certification of six new inventions or six independent sources of profit.
- **Zero candidates passed the frozen exploratory screen.** ETH SMA-40 was a positive historical lead but failed the later-episode and drawdown criteria.

Under one useful economic taxonomy, these templates largely cover absolute-trend continuation, trend-conditioned reversion and relative-strength allocation. That three-way grouping is an analyst classification, not an objective independence count. The previous study supports a narrow exploratory search; it cannot satisfy a request for 100 or 10,000 structurally original systems.

## Feasibility of a 10,000-system target

Generating 10,000 JSON rows, formulas or configuration IDs is technically straightforward. Establishing 10,000 material mathematical identities, implementing their accounting/execution contracts, acquiring appropriate data and demonstrating net performance is a different undertaking. No evidence supplied here supports a promise that all those stages can be completed for exactly 10,000 systems.

At 10,000 accepted identities, exhaustive pairwise comparisons contain 49,995,000 pairs. Canonicalization, provenance and hierarchical family review can reduce redundant checks, but a hash or low signal correlation cannot substitute for semantic review. The accepted count should increase only when an identity card passes review. Rejected duplicates and attempted evaluations stay in the ledger; never pad the count to meet a target.

Start with a sourced tranche spanning materially different mechanisms and data requirements. Choose a representative from each applicable class, define its exact evidence contract, implement and audit it, then expand only when the next class is both structurally distinct and testable. This is a proposed process, not a reduction of the user's numerical target or a claim to have completed it.

## Evidence ladder and fair comparisons

| Stage | Evidence earned | Appropriate claim |
|---|---|---|
| 0 — Provenance and identity | Equations, source, mechanism, nearest-neighbor comparison | Documented hypothesis; distinctness accepted or unresolved |
| 1 — Implementation invariants | Prefix causality, state/reset checks, funded ledger, costs, synthetic failure cases | Implementation behaves as specified |
| 2 — Mechanism/data viability | Correct observable variables, aligned timestamps, plausible cost scale | Empirical experiment is feasible |
| 3 — Exploratory replay | Full search ledger, appropriate execution model, fixed risk contract, all failures retained | Historical result on reused data |
| 4 — Frozen external/prospective test | Predeclared model, controls and stopping criteria; subsequently observed data | Evidence of performance within that test and its uncertainty |
| 5 — Operational execution validation | Measured fill/reject/shortfall, reconciliation and risk behavior | Execution assumptions supported at measured scale |
| 6 — Deployment decision | All applicable evidence and explicit capital/risk authorization | A bounded operating decision, never a future-profit guarantee |

Use separate execution models for different systems:

| System class | Required evidence/model | What daily spot OHLC cannot establish |
|---|---|---|
| Slow funded spot direction | Native bars with availability times, funded cash/inventory, side costs, gaps, terminal valuation | Exact executable spread/depth or intraday stops |
| Relative value or pairs | Synchronized legs, causal hedge estimates, separate side costs, hedge/leg risk and any borrowing | Simultaneous fills or affordable short inventory |
| Futures/perpetual carry or basis | Native contract definition, synchronized spot/derivative prices, funding events, collateral and liquidation cash flows | Funding payments, contract-specific P&L or margin survival |
| Order-flow prediction | Sequenced trade/book events, receive/exchange times, decision latency and target horizon | Order-flow information or price response at executable latency |
| Market making or execution control | Order events, queue/priority evidence where available, conservative fill model, cancel delays, inventory and adverse selection | A limit order filled merely because a candle touched its price |
| Cross-venue arbitrage | Synchronized executable quotes, balances on both venues, rejection/latency and settlement constraints | Simultaneous capture of two historical best prices |

The current common.py daily evaluator is suitable only for its declared funded long/cash proxy experiment. Kraken documents its OHLC endpoint as a limited recent-bar feed with an unfinished final row; retrieving more copies does not create book or funding histories. [Kraken OHLC documentation](https://docs.kraken.com/api-reference/market-data/get-ohlc-data).

Use a shared *reporting* contract across comparable cohorts: all-in account equity, committed capital, gross and net exposure, common calendar, cost decomposition, drawdown and tail diagnostics, turnover, capacity, rejected fills and uncertainty. Do not impose the same invalid fill simulator on all cohorts. Apply causal risk scaling ex ante; report actual realized exposure. A spot cash account and a leveraged derivatives account are not equal-risk merely because both display $10,000 equity. Cohorts with different observation periods or data quality should not be combined into one universal “best” ranking.

## Controls for searching many alternatives

Preserve every trial that influenced selection, including variants later merged into the same structural family. White's Reality Check tests whether the best candidate found during a specification search improves on a benchmark, explicitly addressing repeated use of the same data. Use a documented implementation only where its data and dependence assumptions are defensible; cross-cohort comparability must be established first. [White, A Reality Check for Data Snooping](https://onlinelibrary.wiley.com/doi/10.1111/1468-0262.00152).

The Deflated Sharpe Ratio addresses selection inflation and non-normal return effects; its independent-trial quantity is not the raw number of names in a registry. Estimating dependence does not justify deleting unsuccessful trials. Short, sparse records and unstable return moments limit interpretation here. [Bailey and López de Prado, The Deflated Sharpe Ratio](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf).

PBO/CSCV can diagnose how a selection process degrades across recombinations of available history. It is not a newly collected chronological test, and recombining dates cannot erase this repository's prior reuse. [Bailey et al., The Probability of Backtest Overfitting](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf).

For scale: a nominal 5% threshold split across 10,000 tests is 0.000005. With 20,000 bootstrap repetitions, that extreme tail contains only 0.1 expected repetitions. Simply extending the previous study's percentile calculation to “10,000-trial adjusted” would provide essentially no tail resolution. More repetitions do not repair biased selection, nonstationarity, invalid resampling or unobserved execution.

There is no universal required trade count. Calendar coverage, effect size, serial dependence and the test's power matter. The existing selected slow rule produced ten closed episodes across 617 days; if its historical rate persisted, another ten would take about 617 days, an arithmetic illustration rather than a prediction. Days or weeks can validate data capture and execution behavior, but cannot establish a sparse rule's dependable profit. Searching more systems or spawning more agents does not accelerate the arrival of independent future market regimes.

## Recommended immediate deliverable

Create a machine-readable identity registry implementing the fields above, import the six previous templates with honest lineage, and assess a first sourced tranche of genuinely different mechanisms. For each, state exactly which dataset and accounting/execution model are available or missing. Implement only those whose empirical contract can be honored, while collecting the missing prospective data. Report accepted identities, duplicate rejections, runnable systems and profitable-evidence status separately.

The protocol itself creates no trading implementation. During this review, the parent team completed an initial two-model tranche. The independent audit below shows why even that count must be separated from the count of nonbaseline fitted trading policies.

## Completed two-model tranche: independent audit and count

`changepoint.py` implements full-bank Bayesian run-length filtering with conjugate normal-inverse-gamma observations. `hmm.py` implements a three-state Gaussian hidden Markov model fitted by regularized EM to the first 90 observed returns, then frozen with forward filtering thereafter. These are two materially different inference templates based on established mathematics; they are not original mathematical inventions. Their source methods describe inference, not guaranteed trading profits. [Adams and MacKay, Bayesian Online Changepoint Detection](https://arxiv.org/abs/0710.3742); [Rabiner, A Tutorial on Hidden Markov Models](https://web.ece.ucsb.edu/Faculty/Rabiner/ece259/Reprints/tutorial%20on%20hmm%20and%20applications.pdf).

`prototype-audit.py` and `prototype-audit.json` record successful independent checks: all 64 binary reset/growth histories for six observations against BOCPD; all 81 latent-state paths for four observations against HMM; an independent probability-domain implementation of all 40 regularized EM updates; 20 real-data prefix checks; eight development-only replays; 96 independently reconciled ledgers; source/spec/output hashes; and development selection/nomination consistency. These checks support mathematical implementation and cash-flow correctness within the declared daily proxy model.

**The fitted HMM trading rule is redundant with buy-and-hold.** Under its frozen initial fit, fourteen-day expected log growth from each pure state is 0.0297262, 0.0318045 and 0.0583072, all above the 0.01660034 entry hurdle. The forecast is linear in the posterior. Therefore every possible posterior mixture triggers long after training, irrespective of subsequent observations. Its fitted means include negative states; the redundancy arises from the multi-step transition/forecast policy, not from all means being positive. All 16 window/scenario ledgers exactly match ETH buy-and-hold. This is a formal policy-equivalence result conditional on the frozen learned model, stronger than an observation of matching trades.

Consequently this tranche contains **two implemented inference prototypes, one nonbaseline fitted decision policy, zero new validated profitable systems, and zero original mathematical inventions**. Neither candidate passes its exploratory nomination criteria. BOCPD is selected only because its development result is zero-trade cash while HMM loses. BOCPD loses $122.18 base/$118.31 combined in later 2025 and in the continuous run; recent 2026 has no trades. HMM continuous net is -$296.88 base/-$330.71 combined. The earlier ETH SMA-40 control remains a reused-data lead, not a new method or a validated winner.

These outcomes reinforce the protocol: a new inference model can still produce an old trading policy, and correctly implemented mathematics can still lose money. The request for 10,000 distinct systems remains incomplete; no runtime or deployment changed.
